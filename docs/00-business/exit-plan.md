# [[撤退計画]] — 撤退ラインと最低コスト退避先

作成日: 2026-07-25
前提: 需要検証を省略して実装に進み、**ダメなら早く畳む**方針。ただし**娘の学習用としてコア機能は残す**。

---

## 0. 結論

| 項目 | 結論 |
|---|---|
| **金銭的な最大損失** | **約5万円**（公開後6ヶ月運用＋ドメイン＋返金） |
| **時間的な投資** | 約120時間（週10時間 × 3ヶ月）＋運用 |
| **撤退ライン** | **公開6ヶ月で有料10人未満**（他に3条件、§2） |
| **退避先** | **Plan A：無料版として継続。運用コスト実質ゼロ**（§4） |
| **最重要** | **撤退ラインより、撤退コストを下げる事前の設計判断**（§3）。ここを外すと畳めなくなる |

**この事業は「畳みやすさ」を設計に織り込める。** 固定費が月7,900円しかなく、Supabaseは素のPostgresで持ち出し自由、コア機能（作文）と有料機能（記事フィード）を疎結合にできる。**撤退を前提にした設計が、そのまま良い設計になる**。

---

## 1. そもそもの投資規模

撤退ラインを引く前に、**何を失うのか**を確定させる。

### 1.1 金銭

| 項目 | 金額 | 備考 |
|---|---|---|
| 開発期間（約3ヶ月） | **約0円** | Supabase Free + Vercel Hobby で開発可能。課金は公開時から |
| 公開後の固定費 | 7,900円/月 | 6ヶ月なら47,400円 |
| ドメイン | 1,500円/年 | |
| 撤退時の返金 | **月額のみなら最終月分** | §3.1の設計判断で最小化する |
| **合計（6ヶ月で撤退）** | **約5万円** | |

**月7,900円は、失っても生活に影響しない額**。判断を歪めるほどの金額ではない。

### 1.2 時間（こちらが本体）

- 開発：週10時間 × 3ヶ月 ≒ **120時間**
- 運用：問い合わせ対応、障害対応、プロンプト調整で月5〜10時間

**リスクの実体は金ではなく時間。** したがって撤退ラインも「いくら損したか」ではなく「**時間を投じ続ける価値があるか**」で引く。

## 2. 撤退ライン

**4つのうち1つでも該当したら撤退を検討、2つ以上なら撤退。**

### 撤退ライン①：会員数（時限式）

| 時点 | 有料会員 | 判定 |
|---|---|---|
| 公開3ヶ月 | **5人未満** | 黄信号。訴求か商品を1回作り直す |
| **公開6ヶ月** | **10人未満**（＝損益分岐点） | **撤退** |
| 公開12ヶ月 | 30人未満 | 撤退（続けても月2万円に届かない） |

**6ヶ月で分岐点に届かないなら、その先も届かない。** 個人開発の集客は指数関数的には伸びない。

### 撤退ライン②：継続率

**3ヶ月継続率が40%を切ったら撤退。**

集客が弱いのは改善余地があるが、**入った人がすぐ辞めるのは商品が成立していない証拠**。会員数が目標に届いていても、この条件に該当したら撤退する。

### 撤退ライン③：時間対効果

**月間の運用時間が10時間を超え、かつ月次利益が2万円未満の状態が3ヶ月続いたら撤退。**

時給2,000円を割る。それなら本業か別のことに時間を使ったほうがいい。

### 撤退ライン④：自分と娘が使わなくなった

**最も信頼できる指標。** 作者が使わないツールは他人も使わない。数字がどうであれ、2週間連続で自分も娘も開かなくなったら、事業として続ける理由を問い直す。

### 撤退しない条件（重要）

**娘が日常的に使っている場合、コア機能は絶対に止めない。**
Plan A（§4.1）の運用コストは実質ゼロなので、事業として撤退しても**サービスを止める必要はない**。「事業の撤退」と「サービスの終了」を切り離して考える。

## 3. 撤退コストを下げる事前の設計判断 ★本書の核心

**撤退ラインを決めることより、こちらのほうが重要。** 以下を最初にやっておかないと、畳みたくても畳めなくなる。

### 3.1 年払いを最初は出さない（月額のみ）

| | 月額のみ | 年払いあり |
|---|---|---|
| 撤退時の返金 | 最終月分のみ（または日割り） | **残期間全額の返金義務が生じうる** |
| 撤退の告知期間 | 30日で足りる | 最長11ヶ月分の債務を抱える |
| キャッシュフロー | 弱い | 強い |

**最初の6ヶ月は月額のみで出す。** 撤退ラインを通過して継続を決めた時点で年払いを追加する。

年払いは解約率を下げる強力な武器だが、**撤退を前提にする段階では足枷になる**。`pricing-plan.md` §0 の年額プランは、継続判断後に導入する。

### 3.2 記事フィードをコアから疎結合にする

**撤退＝有料機能の停止**であり、コア機能（作文・翻訳・発音・保存・失敗履歴）は残す。そのために最初から分離しておく。

| 層 | コア（残す） | 記事フィード（止める） |
|---|---|---|
| テーブル | `profiles` `sentences` `words` `fails` `practices` | `sources` `raw_articles` `lessons` `lesson_vocab` `lesson_reads` `interests` `lesson_requests` |
| Edge Function | `/translate` `/keywords` `/pinyin` | `/lessons/*` `cron_*` |
| 画面 | 作文・履歴・プレイヤー | フィード一覧・記事詳細・リクエスト・興味設定 |
| 外部依存 | LLM API のみ | LLM API＋情報源＋cron |

**撤退操作は「pg_cron を止める」「フィード系画面をフラグで隠す」の2つだけ**で済む状態にしておく。テーブルを削除する必要すらない。

**やってはいけないこと**：`sentences` テーブルに `lesson_id` を持たせるなど、コアがフィードに依存する構造を作ること。依存は**フィード→コアの一方向**に限定する（記事の語彙を `words` に登録するのはOK）。

### 3.3 データポータビリティを最初から確保する

- **Supabase（素のPostgres）を選んだのは撤退の観点でも正解**。`pg_dump` で全部持ち出せる。Firestore を選んでいたら移行コストが跳ねていた
- 現行の `sentences.md` / `words.md` 生成ロジックを**エクスポート機能として残す**。撤退時にユーザーへ返すデータ形式がすぐ用意できる
- 月1回、自動で `pg_dump` をローカルに退避する仕組みを Phase 1 の時点で入れる

### 3.4 規約に終了条項を最初から書く

利用規約と特商法表記に以下を明記しておく。後から追加すると既存会員への不利益変更になる。

- **サービス終了時は30日前に告知する**
- 終了時の未経過分の取扱い（月額なので「最終月は課金しない」が最も簡潔）
- ユーザーデータのエクスポート期間（終了後30日間はダウンロード可能、等）
- 個人開発である旨と、サポート範囲の限定

### 3.5 開発期間中は課金しない

Supabase Free + Vercel Hobby で開発する。**Supabase Pro に切り替えるのは公開の直前**。これで開発3ヶ月分（約24,000円）が浮く。

> Supabase Free の「1週間無操作で一時停止」は、開発中は自分が触るので問題にならない。

### 3.6 Stripe は最初から Customer Portal を有効にする

撤退時、**全会員のサブスクリプションを一括キャンセルできる状態**にしておく。Stripe ダッシュボードから可能だが、事前に手順を確認しておくこと。

## 4. 退避先（撤退後の構成）

> ★ **方針変更（2026-07-25）**：Plan A を「撤退先」ではなく **「出発点」** にする。
> 家族版を先にリリースし、2ヶ月使ってから収益化を判断する（`../30-research/saas-migration-study.md` §8.0）。
> **これにより「撤退」という工程自体が消える。** 家族版は常に動いており、収益化を足すか足さないかを選ぶだけになる。
> 以下の §4.1 は、有料化した後に事業を畳む場合の「戻り先」として引き続き有効。

### 4.1 Plan A：無料版として継続 ★本命

**娘と自分（＋希望者数人）が使い続けるための構成。運用コスト実質ゼロ。**

| 項目 | 構成 | 月額 |
|---|---|---|
| DB・認証 | **Supabase Free**（500MB DB、50,000 MAU、5GB egress） | **0円** |
| ホスティング | Cloudflare Pages または Vercel Hobby | **0円** |
| LLM | Gemini 2.5 Flash-Lite 従量 | **約7円**（3人 × 月150文） |
| ドメイン | 継続するなら | 125円 |
| **合計** | | **約130円/月** |

**家族数人なら Supabase の無料枠に余裕で収まる。**
「1週間無操作で一時停止」の制約は、**娘が毎日使うなら発生しない**（万一停止してもダッシュボードから復帰可能）。

**移行作業**：
1. pg_cron を停止（記事フィードの生成を止める）
2. フィード系UIをフラグで非表示
3. Stripe のサブスクを全キャンセル、Product を無効化
4. Supabase を Pro → Free にダウングレード（**要注意**：Free は500MB上限。`raw_articles` と `lessons` が大きければ先に削除するかダンプして退避）
5. Vercel Pro → Hobby にダウングレード

**所要時間：半日程度。**

### 4.2 Plan B：ローカル構成に回帰

**Plan A が何らかの理由で使えない場合の保険。**

現在の `server.py` + `index.html` + Ollama + Tailscale 構成に戻す。**このコードは git 履歴に残っているので、いつでも復元できる**。

| メリット | デメリット |
|---|---|
| **完全に無料**（クラウド依存ゼロ） | Mac を起動し続ける必要がある |
| データが手元にある | 外出先からは Tailscale 必須 |
| 既に動作実績がある | 娘に使わせるには少し不便 |

**Plan A のほうが娘にとって使い勝手が良い**（Macの起動状態に依存しない）ので、Plan B は保険と位置づける。

> **重要**：移行時に `server.py` 系のファイルを削除しないこと。git に残っていても、動く状態のブランチを1本残しておくと復帰が早い。

### 4.3 Plan C：完全終了

娘も使わなくなった場合。

1. 全ユーザーに30日前告知
2. エクスポート機能を案内（JSON / Markdown）
3. `pg_dump` で全データを退避してローカル保管
4. Supabase / Vercel / Stripe / ドメインを解約

## 5. 撤退実務チェックリスト

撤退を決めてから実行するまでの手順。**告知が先、停止が後**。

### 5.1 事前（決定〜告知）

- [ ] 撤退ライン該当を確認し、日付を記録する
- [ ] 終了日を決める（**告知から最低30日後**）
- [ ] **新規登録を停止**（これを最初にやる。決めた後に新規を取ると不誠実）

### 5.2 告知

- [ ] 有料会員へメール告知（終了日、課金停止日、データ取得方法、返金の有無）
- [ ] アプリ内バナー
- [ ] 特商法表記・利用規約に沿った内容になっているか確認

### 5.3 課金の停止

- [ ] **Stripe で全サブスクリプションをキャンセル**（次回請求が発生しないことを確認）
- [ ] Product / Price を無効化
- [ ] 最終月の課金を停止または返金
- [ ] **返金が発生する場合、元取引の決済手数料3.6%は戻らない**点を織り込む

### 5.4 データ

- [ ] エクスポート機能が全ユーザーで動くことを確認
- [ ] 終了後30日間はダウンロード可能な状態を維持
- [ ] `pg_dump` で全データをローカルに退避
- [ ] 退避後、**個人情報保護法の観点から不要な個人データを削除**（保有し続ける理由がないため）

### 5.5 縮退（Plan A へ）

- [ ] pg_cron 停止
- [ ] フィード系UI非表示
- [ ] `raw_articles` / `lessons` を整理（Free枠500MBに収める）
- [ ] Supabase Pro → Free、Vercel Pro → Hobby
- [ ] **娘のアカウントで動作確認**（ここが最終目的）

## 6. 判断を早めるための計測

撤退ラインを機能させるには、**毎月同じ数字を見る**必要がある。以下を月次で記録する。

| 指標 | 取得元 | 撤退ラインとの関係 |
|---|---|---|
| 有料会員数 | `subscriptions` テーブル | ライン① |
| 新規登録数 / 解約数 | Stripe | ライン① |
| 3ヶ月継続率 | `subscriptions` の履歴 | **ライン②** |
| 自分の運用時間 | 手動記録 | ライン③ |
| 月次利益 | 売上 − 固定費 − LLM原価 | ライン③ |
| **自分と娘の最終利用日** | `practices` テーブル | **ライン④** |

**特に「自分と娘の最終利用日」は自動で取れる**（`practices` に記録が残る）。ダッシュボードに出しておくと、ライン④の判定が主観に流されない。

## 7. この計画の要点

1. **金銭リスクは約5万円**。判断を歪めるほどの額ではない。時間のほうが本体
2. **撤退ラインは公開6ヶ月で有料10人**。他に継続率40%、時給2,000円、自分が使わなくなったら
3. **年払いを最初は出さない**。これが撤退コストを最も左右する
4. **コアと記事フィードを疎結合にする**。撤退＝cron停止＋UI非表示で済む状態を作る
5. **撤退してもサービスは止めない**。Plan A の運用コストは月130円。娘のために残す
6. **「事業の撤退」と「サービスの終了」は別物**として設計する
