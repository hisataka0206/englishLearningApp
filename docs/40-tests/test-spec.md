# 現行アプリ テスト仕様書

対象実装: `apps/local/`（v1.37.1） / 基準文書: `../10-specs/current-app-spec.md`
作成日: 2026-07-26

> **目的は「アプリが動くこと」の確認ではなく、`../10-specs/current-app-spec.md` の記述が実装と一致することの確認。**
> 各テストは仕様書の特定の記述を参照し、**仕様書がそう書いているから、そう振る舞うはずだ**という形で期待値を立てる。
> 失敗した場合は「実装のバグ」か「仕様書の誤り」かを切り分ける（`test-report.md` に記録）。

## 1. テストの層と範囲

| 層 | 対象 | 実行方法 | 自動化 |
|---|---|---|---|
| **L1** | サーバー内部ロジック（純粋関数） | Python 直接呼び出し | ✅ |
| **L2** | クライアント分割ロジック・LABELS | `index.html` からJSを抽出して Node で実行 | ✅ |
| **L3** | HTTP API 契約 | サーバーを一時データディレクトリで起動し実際にHTTPを叩く | ✅ |
| **L4** | 外部サービス連携（Ollama / Azure / Notion / Drive） | — | ❌ **範囲外** |
| **L5** | UI操作・音声合成・録音 | 実機での目視・聴取 | ❌ **手動**（§7にチェックリスト） |

**L4を範囲外とする理由:** 課金・鍵・ネットワークを伴い、CIで反復実行できない。これらは仕様書の記述対象としても「外部APIをこう呼ぶ」という接続仕様であり、内部ロジックの正しさとは分離できる。

**判定基準:** L1〜L3が**全件合格**であることをもって「仕様書と実装が一致している」とみなす。L5は別途、手動で確認する。

## 4. L3: HTTP API 契約

一時ディレクトリをデータ領域として実サーバーを起動し、HTTPで叩く。
**Ollama・Azure・Notion・Driveを使わない経路のみ**を対象とする。

> **★実データ保護（必須）**
> `GET /api/health` は `global CFG; CFG = load_config()` で**設定を再読込する副作用**を持つ（§6 の注記）。
> テスト時にこれを塞がないと、health を叩いた瞬間にデータ領域の隔離が外れ、**利用者の実データを書き換えてしまう**。
> したがって L3 では `load_config` / `make_drive` / `make_notion` / `make_azure` をスタブに差し替え、
> **health 呼び出し後にもデータ領域が一時ディレクトリのままであること（A-00）**を明示的に検査する。

| ID | 対象 | 検証内容 | 仕様書の該当 |
|---|---|---|---|
| A-00 | **実データ保護** | health のconfig再読込後もデータ領域が隔離されている | §6（healthの副作用） |
| A-01 | 共通エンベロープ | 成功時 `{ok:true, data:{...}}` / 失敗時 `{ok:false, error:"..."}` | §6 冒頭 |
| A-02 | `GET /api/health` | `version`/`models`/`fail_labels`/`article_fail_labels` 等のキーが揃う | §6 |
| A-03 | `POST /api/sentences` | `{id}` を返す。IDは32桁hex | §6・§10 |
| A-04 | `POST /api/sentences`（id付き） | `{id, updated:true}` を返し、**新規作成されない** | §6 |
| A-05 | `GET /api/sentences?lang=zh` | zh で保存した文が返り、en には**混ざらない** | §7 #33 |
| A-06 | `POST /api/words` → `GET /api/words` | 保存した単語が取得できる | §6 |
| A-07 | `POST /api/practice` | `{practice_count, last_practiced}` を返し、回数が増える | §6 |
| A-08 | `POST /api/delete` | `{deleted}` を返し、一覧から消える | §6 |
| A-09 | `POST /api/pinyin` | `{pinyins, pairs, words}` の**3キー**を返す | §6（修正箇所） |
| A-10 | `POST /api/assessments/clear` | **`/api/assess` の前方一致に飲み込まれない**（回帰テスト）。`{deleted}` を返す | §6 |
| A-11 | `GET /api/assessments?mode=weak` | 苦手一覧の形式で返る | §6 |
| A-12 | 未知のパス | 404 を返す | — |
| A-13 | 不正なJSON body | 500系で落ちず `{ok:false}` を返す | §6 |
| A-14 | `created` の形式 | `%Y-%m-%d %H:%M:%S`（TZなし） | §10 |
| A-15 | 保存レコードの構造 | §10 の sentence/word のフィールドが揃う | §10 |
| A-99 | **実データ保護（事後）** | テスト終了後、実データにテストレコードが混入していない | — |

## 5. 合否判定

- **合格**: 期待結果と実際が一致
- **不合格**: 一致しない。原因を次の2つに切り分けて記録する
  - **実装の不具合** → 実装を直す（または仕様書に「既知の不具合」として明記）
  - **仕様書の誤り** → 仕様書を直す
- **範囲外**: L4/L5

**全体の合格条件: L1〜L3 の全テストが合格。**
