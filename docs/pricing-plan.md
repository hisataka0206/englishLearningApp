# English Learning App — [[料金プラン設計]]

作成日: 2026-07-25 / 更新: 収益モデルを「[[記事教材の自動生成]]」課金に変更
前提: [[PWA]]（Web直販）+ [[Stripe]] / 為替は **1 USD = 150円** と仮定

---

## 0. 結論

**無料＝自分で作文する道具。有料＝自分の興味に沿った学習教材が自動で作られる。**

| プラン | 月額 | 年額（月換算） | 内容 |
|---|---|---|---|
| **Free** | 0円 | — | 作文・翻訳・発音・保存・失敗履歴（**月150文**）／記事は月3本まで味見 |
| **Standard** | **980円** | **9,800円**（817円） | 記事リクエスト月20本 / 共有プール閲覧無制限 / 英語＋中国語 |
| **Pro** | **1,980円** | **19,800円**（1,650円） | 記事リクエスト月100本 / 高品質モデル / レベル調整・深掘り |

**損益分岐点：有料会員 13人**（無料ユーザーの原価負担を織り込んだ実効値）
**Standard/Pro が 8:2 で混ざる想定なら 10人**

原価構造は前バージョンから大きく変わらない。**記事1本の生成原価は約1.7円**にすぎず、しかも**生成した記事を全ユーザーで共有する設計により、ユーザーが増えるほど1人あたり原価が下がる**。

## 1. モデル変更の要点

### 変更前 → 変更後

| | 変更前 | 変更後 |
|---|---|---|
| 無料 | 月30文まで（お試し扱い） | **作文機能はほぼ全開放**（月150文） |
| 有料の価値 | 「量の制限解除」 | **「教材が自動で作られる」という別種の価値** |
| 課金の説得力 | 弱い（我慢すれば無料で足りる） | **強い（無料では絶対に得られない）** |

### なぜこの変更が良いか

1. **無料と有料が競合しない**。前案は「月30文の壁」が唯一の課金理由だったため、ライトユーザーは永遠に無料で足りてしまう。新案では有料機能が**代替不能**
2. **作業の外部化に対価を払う構造**。現在Notionで手作業している「探す→要約する→語彙を抜く」は、時間で言えば1記事20〜30分。ここを自動化する価値は明確に月1,000円を超える
3. **共有プールが資産として積み上がる**。誰かのリクエストで生成した記事が、同じ興味の別ユーザーにそのまま提供できる。**ユーザーが増えるほど原価効率が上がる稀有な構造**

## 2. 記事1本あたりの生成原価

### 2.1 パイプライン（[[AI書き下ろし型]]）

| 工程 | 使用モデル | input | output |
|---|---|---|---|
| ① 候補記事のスクリーニング（タイトル・抜粋30件から選定） | Gemini 2.5 Flash-Lite | 3,000 | 200 |
| ② 学習用テキストの書き下ろし（ソース2〜3本を読み、対象言語でオリジナル執筆） | gpt-5.4-mini | 9,000 | 800 |
| ③ 重要語彙の抽出＋意味＋例文＋日本語対訳＋ピンイン | Gemini 2.5 Flash-Lite | 2,500 | 1,600 |

### 2.2 モデル構成別の単価

| 構成 | ① | ② | ③ | **合計** |
|---|---|---|---|---|
| 全部 Gemini 2.5 Flash-Lite（最安） | 0.06円 | 0.18円 | 0.13円 | **0.37円/本** |
| ハイブリッド：②を Gemini 3.5 Flash-Lite | 0.06円 | 0.71円 | 0.13円 | **0.90円/本** |
| **ハイブリッド：②を gpt-5.4-mini（推奨）** | 0.06円 | 1.55円 | 0.13円 | **1.74円/本** |

**推奨は gpt-5.4-mini 構成（1.74円/本）**。理由は、この機能の価値の99%が**②の書き下ろしの質**に集中しているため。ここをケチると商品自体が成立しない。逆に①③は機械的な作業なので最安モデルで十分。

**1本1.74円は、手作業20〜30分の代替として桁違いに安い。** 原価は制約条件にならない。

### 2.3 音声はゼロ円のまま

生成した記事の音読も [[Web Speech API]]（ブラウザ内蔵）で処理する。**記事教材化しても発音機能の原価は増えない**。ここが競合との構造的な差。

## 3. 共有プールが効く仕組み

「リクエストされたら作る、作ったものは同じ興味を持つ人にも共有する」設計では、ユーザーが増えるほど**プールのヒット率**が上がり、新規生成の必要本数が減る。

| 有料会員数 | 想定ヒット率 | 月20本閲覧のうち新規生成 | 1人あたり記事原価 |
|---|---|---|---|
| 10人 | 20% | 16本 | 27.8円 |
| 100人 | 50% | 10本 | 17.4円 |
| 1,000人 | 75% | 5本 | 8.7円 |
| 10,000人 | 85% | 3本 | 5.2円 |

**以降の試算はすべて「ヒット率50%（新規10本）」の中間値**で計算する。初期は原価が少し高く、成長すると自然に下がる。

### 設計上の注意

- ニュースには**鮮度**があるため、同じキーワードでも1週間前の記事は再利用しにくい。**「キーワード×日付」でキャッシュし、有効期間は3〜7日**とするのが現実的
- 人気カテゴリ（AI・ヒューマノイド・EV等）は**リクエストを待たず1日2本を定期生成**しておく。これでヒット率が跳ね上がり、かつ「開いたら新着がある」体験が作れる。この定期生成分（月600本＝約1,046円）は固定費として計上する

## 4. 固定費

| 項目 | 月額 | 備考 |
|---|---|---|
| Supabase Pro | 3,750円 | $25。無料枠は1週間無操作で停止するため本番必須 |
| ホスティング（Vercel Pro） | 3,000円 | $20。Hobbyは非商用限定 |
| **Firecrawl Hobby** | 2,400円 | $16。5,000ページ/月。RSSのないサイトの本文取得用 |
| **人気カテゴリの定期生成** | 1,046円 | 月600本 × 1.74円 |
| ドメイン | 125円 | 年1,500円 |
| **合計** | **約10,300円/月** | |

### 増減要因

- **RSSのあるサイトだけに絞れば Firecrawl は不要**（-2,400円）。事前選定サイトの選び方で月額が変わる
- ボット保護の強いサイトを含めると、Firecrawl のクレジット消費が10〜25倍になり上位プランが必要
- 静的配信を Cloudflare Pages、APIを Supabase Edge Functions に寄せれば Vercel Pro を省ける可能性（要検証、-3,000円）
- 埋め込み検索は Supabase の全文検索／pgvector で足りるため**追加費用ゼロ**（Embedding APIを使っても月$0.06程度で無視できる）

### Free（0円）

| 項目 | 内容 |
|---|---|

| 発音プレイヤー | フル機能 |

| 言語 | 英語＋中国語 |
| 記事教材 | **月3本まで**（味見。カテゴリは選べるが本数制限） |
| 弱点レポート | 簡易版 |

**設計意図**：作文まわりは気持ちよく使い切ってもらう。ここで「このアプリは自分に合う」と分かった人だけが、記事機能の3本を消費して「これは自分では作れない」と実感する導線。

**なぜ月150文の上限が必要か（重要）**

「作文は無料・無制限」にすると、無料ユーザー1人あたり月8.8円（600文想定）の原価が発生する。有料100人・無料3,333人の段階で**月29,300円**、有料1,000人・無料33,333人では**月293,000円**の純粋な持ち出しになる。

月150文なら1人2.2円に抑えられ、同じ規模でそれぞれ7,400円／73,600円。**「実質使い放題に感じるが青天井ではない」上限が必要**。1日5文は瞬間英作文の練習量として十分現実的で、ほとんどのユーザーは上限を意識しない。

## 10. リスクと注意点

### 10.1 【最重要】Weibo は情報源として使えない

現在Notionで使っている情報収集経路が、**有料サービスの情報源としては成立しない**。

| 論点 | 内容 |
|---|---|
| 個人開発者登録 | Weibo開放プラットフォームの個人開発者登録は**中国の身分証情報の提出が必要**。日本のパスポート・携帯番号で通過できるかは不明 |
| 規約 | 開発者協議2.7.7「APIで取得したデータは接続したアプリにのみ供され、**その他いかなる用途にも使用してはならない**」、2.7.8「データ収集・分析で第三者にサービス提供する開発者は**商業データAPI経由＋別途契約が必須**」 |
| サーバー保存の禁止 | 「第三者のサーバサイドでのユーザーデータ保存を禁止。キャッシュはクライアント側のみ」と明記。**共有プール設計と真っ向から矛盾する** |
| 自動取得 | 「ユーザーの能動的操作でない頻繁な呼び出しは、頻度制限内であってもロボット/悪意的抓取と判定し、appkey・IPを封禁」 |
| レート制限 | 1アプリ・1認可ユーザーあたり**1日100回**。未審査アプリはテストアカウント15個まで |
| RSSHub経由 | Cookie必須・海外IPでは取得内容が劣化・2026年も障害Issue継続。**規約リスクの回避にはならない** |
| 準拠法 | 中国大陸法、専属管轄は北京市海淀区人民法院 |

**対応方針**：中国語ソースは Weibo ではなく、**新聞社・技術メディア・ポータルの公式RSS、企業のプレスリリース、政府系サイト**に切り替える。個人利用（私的使用）としてWeiboを見て回るのは従来通り可能なので、**「自分がWeiboで見つけた話題をキーワードとして投入し、公式ソースで裏取りして書き下ろす」**という運用にすれば、あなたの目利きは資産として残る。

出典: [Weibo 開発者協議](https://open.weibo.com/wiki/%E5%BC%80%E5%8F%91%E8%80%85%E5%8D%8F%E8%AE%AE) / [接口访问频次权限](https://open.weibo.com/wiki/%E6%8E%A5%E5%8F%A3%E8%AE%BF%E9%97%AE%E9%A2%91%E6%AC%A1%E6%9D%83%E9%99%90)

### 10.2 著作権 — 既存パイプラインは「要約型」なので改修が必要

**この項目が、既存パイプラインをそのまま商用転用できない唯一の理由。**

現在Notionで運用しているのは元記事の**要約**。個人利用（私的使用）なら問題ないが、**有料配信となると要約は翻案権に触れうる**。採用方針である[[AI書き下ろし型]]へ寄せる改修が必要になる。

| | 要約型（現行） | 書き下ろし型（商用向け） |
|---|---|---|
| 入力 | 元記事1本 | 複数ソースから**事実だけ**抽出 |
| 出力 | 元記事の内容を圧縮したもの | 学習用に**オリジナルで構成した文章** |
| 元記事との関係 | 構造・論旨をなぞる | 事実を共有するのみ |
| 著作権リスク | 翻案権の問題になりうる | 大幅に低い |
| 学習教材としての質 | 元記事の難易度に引きずられる | **難易度・長さを制御できる**（Proの機能になる） |

改修は難しくない。プロンプトに以下を足すのが中心：

- **ソースを2〜3本読ませ、共通する事実を抽出させる**（1本だけだと構造をなぞりやすい）
- **「原文の言い回し・語順・段落構成をなぞらないこと」を明示的に禁止する**。LLMは放っておくと原文構造を再現する
- 学習目標（対象語彙・難易度・長さ）を先に指定し、**そこから逆算して文章を構成させる**

改修は品質面でもプラスに働く。要約型は元記事の難易度がそのまま出るが、書き下ろし型なら学習者のレベルに合わせられる。**Proプランの「難易度レベル指定」はこの改修の副産物として自然に実現する。**

### 10.2b 「無料で読める」＝「二次利用してよい」ではない

情報源を「無料で記事を配信しているサイト」から選ぶ方針だが、**無料公開と二次利用の許諾は別物**。無料で読めるサイトでも、利用規約で商用の自動取得・二次利用を禁じているのが通常。

事前選定の段階で必ず確認すること：

- **robots.txt**（クローラーの許可範囲）
- **利用規約の「禁止事項」**（自動取得、商用利用、複製、翻案の各条項）
- **RSSの提供有無**（RSSを公開しているサイトは機械可読な配信を前提としており、相対的に安全側）

日本の著作権法30条の4（情報解析目的の利用）／47条の5（軽微利用）の適用範囲は、**有料配信という文脈では慎重な判断が必要**。事前選定サイトのリストが固まった段階で弁護士確認を推奨する。

なお**出典リンクは必ず表示し、原文へ送客する**こと。法的な安全性だけでなく、ソースサイトとの関係を敵対的にしないためにも重要。

### 10.3 Google Custom Search JSON API は使わない

**新規受付終了済み、既存顧客も2027年1月1日でサービス終了**。設計に入れてはいけない。
記事検索は**自前DBに新着記事を蓄積し、Supabaseの全文検索／pgvectorで引く**方式にすれば、外部検索APIそのものが不要になる。

出典: https://developers.google.com/custom-search/v1/overview

| リクエスト機能の乱用 | プラン別の月次上限をサーバー側で厳格に判定。同一キーワードの連投はキャッシュヒット扱いにして原価を発生させない |
| スクレイピングクレジットの枯渇 | Firecrawl等は**翌月繰越なし**。使用量アラートを設定。ボット保護の強いサイトは10〜25倍消費するため事前選定で除外 |
| 生成品質のばらつき | 公開前に自分で50本読んで合格率を測る。**合格率が8割を切るならプロンプトが未完成** |
| ソースサイトの構造変更 | 事前選定サイトのパーサーが壊れる。RSSを優先し、HTML依存を減らす |
| 記事の鮮度切れ | キャッシュ有効期間3〜7日。古い記事はプールに残しつつ「アーカイブ」表示にする |

## 11. 検証すべき順序

### 前提の確認：既に完成している部分

現在Notionで運用している記事生成は、**手作業ではなく既に自動化済み**。手動なのは「Weiboで元記事を探す」工程だけ。つまり：

| 工程 | 状態 |
|---|---|
| ① 情報源から候補記事を集める | **未自動化**（Weiboを人力で見て回っている） |
| ② 候補の中から教材にする価値のあるものを選ぶ | **未自動化**（あなたの目利き） |
| ③ 要約・記事化 | **完成・稼働中** |
| ④ 重要語彙の抽出・記事化 | **完成・稼働中** |

**残作業は①②であって、③④ではない。** そして商品リスクも①②に集中している。

### ボトルネックは「目利きの自動化」

③④が既に動いているなら、生成品質の検証は概ね済んでいる。**本当に難しいのは②** ——「この記事は教材にする価値がある／ない」というあなたの判断を、機械が代替できるか。

現在この判断はWeiboをスクロールしながら無意識にやっているはずで、**言語化されていない**。ここを言語化してプロンプト化できるかが、商品として成立するかの分かれ目になる。

**検証方法**：事前選定サイトから1日分の候補を50件集め、
- あなたが「教材にしたい」と思うものに手で印をつける
- 同じ50件をスクリーニングプロンプトに通す
- **一致率を測る**。7割を切るなら選定基準の言語化が足りない

この作業を2〜3日分やれば、選定基準はかなり具体化できる。

### 順序

1. **ソース選定** — Weibo抜きで、ヒューマノイド／中国語テック情報を安定供給できるサイトを10〜20本リストアップ。**RSSの有無・robots.txt・利用規約を1本ずつ確認**（§10.2参照）
2. **選定基準の言語化と一致率テスト**（上記）
3. **③④パイプラインの商用向け改修** — 要約型 → 書き下ろし型（§10.2）
4. **LPで需要検証** — 「あなたの興味のキーワードで、毎日の学習教材が自動で作られる」で事前登録が集まるか。**50件集まらないなら実装前に立ち止まる**
5. **転換率の実測** — 無料ユーザーの何%が記事機能に課金するか。3%を前提にしているが、記事機能の訴求力次第で5〜10%も狙える（その場合、必要な集客規模は1/2〜1/3になる）

### 原価は推定ではなく実測できる

本書の「1本1.74円」はトークン数の推定値。**既存パイプラインが稼働している以上、実際の消費トークンは測れる**。数本分のAPIレスポンスから `usage` を記録すれば、正確な単価が出る。推定と大きくずれる場合はこの試算を差し替えること。

### 逆算した集客目標（転換率3%の場合）

| 目標月次利益 | 必要な有料会員 | 必要な無料ユーザー |
|---|---|---|
| 3万円 | 48人 | 約1,600人 |
| 10万円 | 132人 | 約4,400人 |
| 30万円 | 370人 | 約12,300人 |

転換率が5%に上がれば、必要な無料ユーザーは6割に減る。**記事機能の訴求は「集客数」より「転換率」で効かせる方が現実的**。
